# Orchestrate Feature

**Composition role: helper.** The project workflow remains the driver. Keep programme context and user decisions in the orchestrator; detailed execution belongs to one ordinary owner. An operative invocation selects that separation regardless of task size/duration. Without a resolved feature create nothing; another feature needs another invocation. Preserve actual project, Git, worktree, external-action and scientific authority.

Distill relevant prior agreements into the launch. Resolve what the owner may decide, what the orchestrator can settle and what remains user-reserved under the actual task authority; do not create another decision form or ask the user to repeat a settled answer.

New ordinary owners default to `gpt-6.1-sol` / `medium`; explicit owner overrides apply per field. Preserve the orchestrator's exact settings. Only the project orchestrator launches exactly one ordinary owner; refuse nested ordinary feature-owner creation. Use the authorized ordinary-task mechanism with fresh context, never a native leaf or inherited fork. An explicit orchestrator profile is a precondition: inspect exposed status and stop on mismatch or an unobservable explicit requirement without changing settings. Resolve project/checkout/ref or intended dirty state, foreign writers/resources and exact required route/profile/context controls. A validated replacement names its mechanism/target; manual supervision exposes the same events for later inspection. Every mode retains actionable blocker, required-gate and terminal delivery. Retain the actual ready identity, host and latest wait cursor; pending creation is not ready. After host-required confirmation return one compact launch receipt unless active supervision was selected. No passive watcher or future-wakeup guarantee follows.

Retain in the existing task/checkpoint the outcome/validation basis, owner identity, authority, scoped delegation/review requests, return route and pending orchestrator assessment. Continue the same feature with a reachable compatible owner. Check actual project/checkout, role/profile, trust/authority and recoverable state; do not reset active work. Same-assignment follow-ups carry deltas; a changed assignment/uncertain continuity needs prior disposition, valid carry-over, invalid assumptions/authority and a complete current contract. Recycle for material incompatibility, unreachable/hidden state, irrecoverable stale conclusions, repeated critical misses after correction or explicit request, not compaction/time alone. All existing-task messages, resets and callbacks omit settings overrides, including `model` and `thinking`, even when null. Creation profiles never authorize settings changes. Report accidental target/fields/values/outcome; do not restore without authorization.

It implements/builds/tests/repairs, integrates and self-reviews, updates affected docs and preserves actual evidence. ## Owner messages and delivery

Resolve routine friction within scope. Send required gates, decisions/exhausted blockers, urgent invalidation and terminal/partial handoffs, not routine ACK/progress chains. Each callback identifies the feature/owner, outcome, material consequence/gap, action/decision needed from the orchestrator and one complete accessible handoff link. Local user updates follow host requirements.

Keep the callback compact and the durable handoff complete. Inline facts needed to choose or safely take the next action; keep commands, full hashes, test/measurement inventories, receipts and repeated constraints in existing linked records unless a specific item changes that action. Preserve consequential caveats, invalidations and unknown resource disposition inline. If the recipient cannot access a reference, supply the needed evidence or report the access gap. Shorten by selecting facts, never joining words/numbers or dropping labels, punctuation or units; impose no hard length cap.

A ready handoff binds actual tested state, criterion evidence and independent review target/verdict; separates validation evidence from unassessed usefulness; and includes limitations, artifacts, pending decisions and resource disposition. Partial, blocked and failed results name unfulfilled scope and any proposed bounded continuation. The owner reports readiness, not acceptance.

Begin the existing handoff with a complete assessment summary of those facts and the next action, then link supporting detail. Do not duplicate evidence inventories or create another artifact solely to shorten a message.

Use the verified native recipient/action with no settings fields. Create/retain request IDs as the route requires, reuse them for retries and retain actual returned identities. Reconcile uncertain outcomes before retrying. Accepted send proves transport acceptance/dispatch, not receiver assessment, validation or closure. Never fabricate IDs, guess routes or switch operations to bypass failure. Preserve failed payload/error and use only an authorized practical fallback; timeout or uninspected manual state remains unobserved.

## Orchestrator receives and acts

On each owner return, recover its task/contract and check the expected identity, assignment and applicable target. Read the linked handoff and decision-bearing evidence. Assess promised scope, actual result, required review, limitations and intended-use validation. Use valid checks/review coverage without routinely repeating the technical audit; inspect decisive source/artifacts for a material gap, conflict or claim.

Use the handoff's assessment summary to select supporting evidence relevant to the decision, rather than loading every linked inventory. Missing, stale or contradictory evidence remains a gap to resolve before relying on the affected claim.

Choose and record an actual next action in the existing task:

- **Ready result:** send a concrete correction, perform already-authorized missing validation, obtain the user's reserved assessment, or record validated acceptance/closure within authority.
- **Question/blocker:** answer within authority, obtain the user-owned choice, or name the actual blocking dependency.
- **Partial/failed work:** retain useful results and send a bounded continuation to the same compatible owner when authorized, or record the truthful disposition and needed decision.
- **Invalidation:** contain affected consumers, preserve original/invalidating evidence and obtain affected correction/review/validation; continue unaffected work.

An owner callback continues the already-authorized workflow. Do not wait for the user to ask for evaluation or ordinary continuation. The next user-facing response states the orchestrator's assessment, validation state and next action; a bare relay is insufficient. An explicit raw-forward/status-only request permits relay labeled unassessed, with the pending responsibility retained. Send the owner a reply only when it changes its next action; no ceremonial receipt ACK is required. Messages never expand existing authority.

Before escalating, consult the task/spec and previous user decisions. If they settle the issue or delegate the choice, apply them and continue. Send an authorized correction/continuation with the remaining outcome, allowed work, applicable state/evidence, affected verification/review and return condition; never ask whether to finish work already requested. Ask the user only for an unresolved reserved choice, required authority outside the mandate, or a validation observation only they can supply. Ask one specific question with known facts, recommendation and consequence, while unaffected work continues. Do not turn forgotten context, routine defects or implementation alternatives into user-owned blockers.

Passing checks, a `ship` verdict and a finished owner chat cannot close the feature. Acceptance criteria may include validation, but completed scope needs applicable intended-use evidence and an authorized decision. Keep Review open when the needed observation/user assessment is pending; name it without polling. Cancellation/supersession remain distinct dispositions. The user decides merge/adoption in this orchestrator chat; a positive review never grants that authority. Close only the promised scope and reconcile pending integration; wait for merge/adoption only when included in that promise.
