# Orchestrate Sol Feature

**Composition role: helper.** Keep the current project-orchestrator protocol or workflow as the driver. It retains program lifecycle, authority, priorities, and completion ownership; this helper performs one bounded launch-readiness, dispatch, reuse, and handoff-routing operation. If the driver forbids task creation, delegation, or the proposed lifecycle change, stop rather than displacing it.

## Terms

- **Project orchestrator:** the current long-lived Sol task that preserves program context and owns program-level decisions.
- **Feature owner:** one ordinary `gpt-5.6-sol` / `high` task that owns a resolved feature's detailed lifecycle and integrated feature-level acceptance.
- **Worker:** a native `gpt-5.6-sol` / `medium` leaf subagent inside the feature owner.
- **Reviewer:** the inner lens's independent `gpt-5.6-sol` / `high` subagent when its escalation rule fires; it is not a worker, so the Sol/medium worker profile does not constrain it.
- **Launch contract:** the distilled authoritative context, scope, state, authority, success, verification, stop, and reporting packet sent to a feature owner.
- **Reset:** the complete reassignment overlay required before compatible feature-task reuse.
- **Recycle:** stop reusing a feature owner and select a fresh one only on a named material boundary or explicit operator request.

## Activate And Resolve Readiness

Use this skill only for the one feature lane named by the explicit invocation. A later unrelated feature requires another explicit invocation.

1. Confirm that a separate feature owner has material value: the work is multi-phase or context-heavy, contains multiple coherent assignments, can progress independently, or the operator explicitly requested this topology. Otherwise recommend keeping the contained work in the current task and return without dispatch.
2. Confirm that the current session is the project orchestrator, not a feature owner or another child created by this topology. A feature owner must refuse nested ordinary-task creation and report the boundary.
3. Consult the native model/status surface when available. Require available evidence to indicate a product-exposed Sol session, preserve the current effort, and never change the orchestrator's model. If identity is not exposed, state that observability limitation and proceed; if evidence indicates a non-Sol session, stop.
4. Inspect the governing driver, project instructions, native saved-project metadata, repository, and intended working state. Stop if the driver forbids dispatch.
5. Resolve the objective, durable references, user decisions, assumptions, unknowns, non-goals, exact intended start state, scope and shared-state ownership, authority, success criteria, verification, stop gates, and reporting contract. Recover locally answerable gaps and use existing durable authority when sufficient. Create or update the smallest project-owned task, issue, PRD, or specification only when the driver permits it and the feature needs it; never create an orchestration ledger.
6. Return without task creation when a material user-owned or difficult-to-reverse launch choice remains.

If both this topology and the inner ordinary Luna task/thread route are requested for the same unresolved feature, stop and ask the operator to select one owner topology.

## Select New Or Reused Ownership

Before every new or reused dispatch, require one active durable writer per checkout by default, counting the project orchestrator and all feature owners. While the feature owner writes, the project orchestrator performs no concurrent durable writes there unless the launch contract assigns disjoint paths and names one owner for Git state, generated artifacts, formatters, build outputs, test databases, ports, devices, and other shared mutable resources. If active-writer state cannot be recovered from recorded launches and native inspection, treat it as unresolved and serialize or ask. Concurrent writers otherwise require disjoint ownership or explicit worktree authority.

Reuse only an exact known task identity whose feature, project, repository, checkout/worktree, branch, trust boundary, authority envelope, lifecycle role, model and effort, and acceptance boundary remain compatible. Treat the project orchestrator's recorded accepted launch result as profile authority; use native inspection to establish the exact task's identity, reachability, current state, and latest repository handoff. A title, summary, or unsupported recollection is never sufficient. Do not reuse a running owner for an incompatible concurrent assignment. If launch provenance is unavailable, create a new owner or ask rather than asserting compatibility.

Before reuse, send a complete reset that states the prior assignment and disposition; facts allowed to carry over; stale assumptions, scope, permissions, authority, decisions, completion claims, and evidence that must not carry over; and the complete new objective, durable references, interfaces, ownership, dependencies, success criteria, verification, stop gates, reporting, and return format. Preserve a compatible task's configured model and effort by omitting per-message overrides.

Recycle only for a material repository, checkout, trust, authority, or permission change; incompatible model or effort; an unrecoverable superseded contract; repeated acceptance-critical miss or stale assumption after correction; hidden unresolved state; unreachable identity; a materially different feature; or explicit operator request. Classify prior disposition and lost continuity before replacement. Never replace a stalled, failed, or blocked owner silently.

## Launch A New Feature Owner

1. Feature-detect the native surfaces for saved-project resolution, ordinary-task creation, explicit model and effort, fresh context, ready-versus-pending identity, inspection, and waiting. If the product cannot set or validate the exact route, `gpt-5.6-sol` / `high` owner profile, target environment, fresh-context boundary, or truthful return behavior, stop and report the missing capability; never substitute silently.
2. Use the native ordinary-task creation surface, never a native subagent spawn. The project orchestrator must not spawn or duplicate the feature's implementation workers directly.
3. Resolve the saved project first. Personal OS and repositories it manages use the existing checkout unless the operator explicitly authorizes a worktree. Other projects follow user and project policy, then the native default when no stricter rule exists. The inner lens's no-worktree-without-operator-approval rule governs an additional worktree created after launch, not a task environment already assigned under this compliant outer policy. Use the exact intended existing branch/ref or explicitly intended working-tree state; never invent either.
4. Create one ordinary task with the exact product-exposed model `gpt-5.6-sol`, reasoning effort `high`, a concise project-and-feature title that distinguishes it from the project orchestrator and sibling feature owners, and fresh context. Send only the complete launch contract; never inherit or paste the full parent conversation. Conversation history is context, not authority.
5. Treat a product-validated creation request as profile provenance, not independent metadata readback. Never use a pending client identity where a ready task identity is required. Report a ready task identity only when returned; otherwise report the pending identity and its limitation truthfully.
6. Report the identity, objective, ordinary-task route, exact requested model/effort, environment and context mode, and return behavior. Explicit invocation authorizes this one ordinary task, not speculative siblings.

## Feature Owner Launch Contract

Include every applicable field and never omit one whose absence can change behavior or authority:

- **Objective:** observable feature outcome.
- **Durable references:** task, issue, specification, decision record, source, and instruction paths.
- **Decisions, assumptions, unknowns, and non-goals:** classify each load-bearing fact and preserve its provenance.
- **Project and starting state:** project identity, repository, checkout/worktree policy, branch/ref, and exact working-tree state.
- **Scope and shared state:** ownership, interfaces, dependencies, sibling boundaries, active writers, Git state, generated artifacts, formatters, build outputs, test databases, ports, devices, and serialized commands.
- **Authority:** local edits, validation, commit, push, pull request, merge, branch and lifecycle operations, external writes, task creation, and delegation exactly as granted. State absent authority when material; never broaden worktree, branch, push, PR, merge, live-install, or external-write authority.
- **Driver and lens:** retain the applicable project workflow as driver, or use this complete contract as the driver contract when none applies. Explicitly invoke `sol-luna-orchestration` for this resolved feature under the operator-authorized launch contract.
- **Worker profile and topology:** the operator selected native `gpt-5.6-sol` / `medium`; Luna is unauthorized unless the operator later changes the profile. Allow only native leaf subagents, forbid workers from delegating, forbid the feature owner from creating another ordinary task, and state that it owns integration, review, and feature-level acceptance. Forbid the inner ordinary Luna task/thread route.
- **Success criteria and artifacts:** observable completion and required outputs.
- **Verification and decision-bearing evidence:** required commands, checks, evidence, and plausible wrong implementations to distinguish where material.
- **Stop/ask and reporting gates:** user-owned decisions, architecture or contract change, unsafe expansion, missing authority or infrastructure, dependency failure, shared-resource conflict, and explicitly required phase gates.
- **Return route:** exact originating task identity and native continuation mechanism when available. If unavailable, do not fabricate one; retain and report the feature-task identity for later native inspection.
- **Final handoff format:** status (`complete`, `blocked`, `partial`, or `failed`); outcome; exact repository, branch, commit, checkout/worktree, and tested state; changed files and artifacts; commands and results; criteria covered; material decisions and divergence; blockers and uncertainty; downstream action; and continuity state.

## Constrain Feature-Owner Delegation

Require the feature owner to apply `sol-luna-orchestration` as a lens while the applicable project workflow or launch contract remains the driver. The explicit lens invocation relayed in this operator-authorized ordinary-task launch contract satisfies the lens's explicit-invocation requirement for this resolved feature.

The feature owner remains planner, integrator, primary reviewer, and acceptance authority. It delegates implementation-depth assignments only to native `gpt-5.6-sol` / `medium` leaf subagents, following the inner lens's worker contracts, context boundaries, continuity, evidence, review, and acceptance rules. It may use the separate native Sol/high reviewer route only when the inner escalation rule fires. It must not create another ordinary feature task, use the ordinary Luna task/thread route, delegate authority, or treat worker reports as acceptance.

## Supervise And Complete

Immediately after a new or reused dispatch, record the non-terminal lane state `launched, awaiting handoff`. Launch is not completion, and this state supports no progress, health, or acceptance claim.

Require the feature owner to report only a required phase gate, a genuine user-owned, architectural, authority, infrastructure, dependency, or shared-resource blocker, or a final classified handoff. Follow through native waiting or inspection only when handling a returned handoff, answering an operator status request, or satisfying a required project gate. Do not poll repeatedly.

At final handoff, verify only the smallest program-level boundary needed for disposition: exact integrated state, acceptance-criterion coverage, decision-bearing evidence, unresolved risk, continuity, and downstream action. Do not routinely rerun current scope-complete checks or reconstruct implementation detail already accepted by the feature owner. Keep external landing subject to existing authority and keep the lane accounted for until it is classified `complete`, `blocked`, `partial`, or `failed`.
