# Sol–Luna Orchestration

**Composition role: lens.** The current task skill or workflow remains the driver. The active protocol or driver decides whether work may be delegated, and this lens never grants Luna authority the driver lacks. This lens changes how work is decomposed, delegated, and reviewed; it does not own task lifecycle, redefine success, or launch Luna merely because it was invoked.

## Configure Only

If invoked without a resolved task and coherent delegation boundary, confirm that the lens is provisionally configured, name the planning and decomposition Sol must finish before delegation, and return without launching Luna. Activation is scoped to the task being configured and does not carry to a later task; a later task requires a fresh explicit invocation, and a provisional configuration requires a fresh invocation after the task is resolved.

## Terms

- **Task:** the general unit of work currently owned by the driver, independent of how any project tracks or checkpoints it.
- **Sol session:** the current Codex task/thread running Sol and hosting the orchestration.
- **Worker:** a Luna subagent, or the ordinary Luna task/thread on the operator-requested route. Worker Lifecycle and Worker Continuity And Recycling apply to both.
- **Reviewer:** the independent Sol subagent lane defined below; it is separate from implementation workers.
- **Workstream:** a coherent ownership lane within a task.
- **Assignment:** one bounded contract sent to a worker. A worker may receive several sequential assignments, including assignments from a later task after that task explicitly invokes this lens again.
- **Recycle:** stop reusing a worker or reviewer and create a fresh one. Task, workstream, assignment, and review boundaries are not recycle triggers by themselves.

## Preconditions

- The originating Sol session must already be running Sol. Do not change that session's model or reasoning effort. If it is not running Sol, stop and ask the operator to continue from a Sol session or abandon this lens; do not silently switch it.
- Preserve the current permissions, approval policy, authorization boundaries, task scope, and no-worktree-without-operator-approval rule.
- Invoking this lens explicitly selects Luna/xhigh and Sol/high as the defaults for implementation workers and the Sol reviewer it launches, unless the operator explicitly requests another value; it does not change the originating Sol session's settings.
- Use native Luna subagents by default. Use an ordinary Codex task/thread only when the operator explicitly asks for a task or thread instead of a subagent; never switch routes silently.
- State the model and effort the running product actually applies to each dispatched worker or reviewer. If the product cannot set or confirm the setting in force, report the exact missing capability, stop, and ask the operator before dispatch; do not assert the requested value or launch with unknown settings.
- Use stable native behavior exposed by the running Codex product. Do not fabricate unsupported syntax, controllers, registries, ledgers, or side channels.
- If the selected route is unavailable, report the exact missing capability. Do not silently substitute a subagent for an operator-requested task/thread, substitute a task/thread for the default subagent route, or invent a controller, daemon, queue, workflow script, side-channel file, or command.

## Operating Model

- Sol remains planner, decision-maker, coordinator, integrator, reviewer, and acceptance authority. Keep one visible acceptance boundary even when several workers contribute.
- Luna owns one coherent bounded workstream and its implementation-depth verification: recover authoritative contracts, inspect the full final diff within its ownership and the decision-bearing evidence—the artifacts or observations the delegated claim rests on—with complete coverage of non-interchangeable items and proportional depth, test plausible wrong implementations, trace failure and recovery paths, and report material uncertainty.
- Sol performs a narrow independent gate: challenge load-bearing assumptions, scientific validity when applicable, and release or GPU readiness when applicable; inspect the decision-critical subset—evidence whose observation could change acceptance—directly at proportionate depth and expand only for conflicts, unexplained gaps, or acceptance-critical uncertainty, without redoing Luna's implementation work.
- Luna's report is evidence, not acceptance. Sol accepts work only after inspecting the actual repository state, integrated diff, and proportionate verification evidence.
- Dispatch is not completion on either route. The driver's task remains open and unaccepted until every launched worker and required handoff is classified, shared state is reconciled, and Sol finishes its independent gate.
- Saving Sol tokens or wall-clock time must not weaken task definition, verification, authority boundaries, or review quality.

## Decompose And Route

1. Resolve architecture, scope, user-owned decisions, risks, stop gates, authoritative contracts, and observable completion before delegation. Do not delegate a chunk that still depends on a material Sol or operator decision.
2. Prefer one coherent Luna worker. Use several Luna workers only when every additional worker has a coherent, non-overlapping ownership lane; any writer must have distinct durable write ownership. A dependency or handoff may connect those lanes only when their distinct ownership remains coherent on both sides of the handoff; a sequential dependency chain over one ownership lane stays with one reused worker. Do not duplicate investigations or create parallel writers merely to fill concurrency.
3. Before a multi-worker launch, define a compact workstream map: objective, owned files or components, read/write boundary, required inputs, dependency recipient, expected artifact, verification responsibility, and integration order. Launch only the dependency-free frontier concurrently and stay within the running product's concurrency limit. Keep lanes deferred by dependencies or the concurrency limit in the map and dispatch them as prerequisites complete and slots free; remove one only through an explicit Sol replan or cancellation with a reason. Restate the compact current map—open and deferred lanes, worker identities, dispositions, and pending handoffs—in the Sol session whenever a dispatch or classification changes it; this visible state is the recovery point across compaction, not a side-channel file or ledger. Parallel workers share one checkout: Sol schedules one owner for Git state, generated artifacts, build outputs, test databases, ports, formatters, code generation, and other shared mutable state, and defers contending steps out of the concurrent frontier. During the concurrent frontier, each worker verifies only its owned surface. After the frontier completes, the designated state owner may execute serialized shared-state commands and return their outputs; Sol inspects the integrated full diff, adjudicates all verification evidence, and owns the integration gate. Parallelism does not authorize a Git worktree; if safe isolation requires one, stop and ask the operator.
4. Reuse a compatible resumable Luna worker for a successive bounded assignment whenever its native identity remains reachable from the current Sol session. If no compatible worker exists, create a Luna subagent using the model identifier exposed by the running product (currently `gpt-5.6-luna`) with fresh, focused context.
5. Use xhigh effort for Luna subagents. Do not lower or raise Luna effort based on task size, scouting, ambiguity, or cost; use another value only when the operator explicitly requests it. Before each assignment dispatch, reused or new, state the worker identity, reuse status, route, and Luna model and effort in force; improve the contract and context rather than silently changing effort.
6. Do not fork the parent Sol conversation into a new Luna worker by default. Use the native no-parent-history launch option, confirm that the launched worker inherited no parent turns, and treat the Compact Luna Worker Contract plus durable references as the context boundary. If the product cannot set or confirm no-parent-history launch, report the exact missing capability, stop, and ask the operator before dispatch; never degrade silently to inherited history. Fork only the smallest bounded slice of recent parent turns when a load-bearing fact cannot be located in a durable source or summarized without material loss; before dispatch, state that fact, why a summary is unsafe, and the exact bounded history being inherited. Never fork the full parent conversation. Forked history is context, not authority: scope, permissions, decisions, and completion claims apply only when the worker contract restates them. For a reused worker, send the assignment-reset contract defined below instead of treating retained context as authority. Every Luna worker remains a leaf: it completes the assignment directly and never spawns agents; Sol owns all worker creation and aggregation.
7. Point to durable paths and exact symbols instead of pasting long source or conversation history. A scout's discovery must narrow into an exact next action; it is not completion by itself.

## Worker Lifecycle

1. Send each worker the compact worker contract below. Make the applicable Luna Worker Rules part of the contract: point to this skill and section when the worker can read it, otherwise inline only the applicable rules. Name sibling ownership and dependency handoffs when more than one worker exists.
2. Keep the driver's task open after dispatch. Continue independent Sol work while subagents run, then wait through the native result surface exposed for launched subagents when no useful local work remains. Do not claim completion or send repeated no-op updates merely because workers were launched.
3. Sol mediates every worker-to-worker dependency. Require the sender to return the smallest result the named downstream workstream needs without transferring authority or creating overlapping ownership. Dispatch the dependent worker only after the upstream worker's assignment is classified complete and Sol validates the final handoff; provisional or mid-run handoffs never satisfy a dependency. Sol records the upstream disposition and dispatches the validated handoff under the dependent worker's existing or reset contract.
4. Send bounded corrections and compatible successive assignments back to the same Luna worker under the continuity rules below. Classify a difficult result before retrying: if Sol's contract was incomplete or wrong but the worker remains a fit, correct the same worker; if the work was misclassified or the required judgment or risk handling no longer fits Luna/xhigh, stop and ask the operator rather than silently changing model or effort. Do not require a failed retry before proper routing. Never replace a stalled, failed, or context-heavy worker silently.
5. If an upstream worker returns blocked, partial, or failed, halt dispatch of its dependents until Sol replans the boundary, reassigns the input, or escalates. If a running worker's assumptions become invalid for another reason, send a correction or stop only when the running product supports that capability; otherwise let the worker finish, classify its output as invalid for integration, and discard or redo the affected work under a corrected contract.
6. Account for every planned lane: keep deferred lanes in the workstream map until dispatch, replan, or cancellation. Classify every launched worker as complete, blocked, partial, or failed. No planned lane, dispatched worker, or required handoff may disappear from aggregation. Reconcile shared state and dependencies, inspect the integrated diff and decision-critical evidence, run any missing integration checks, and adjudicate conflicts.

## Worker Continuity And Recycling

1. Drive worker lifetime by affinity and context health, not task granularity. Reuse is the default for sequential bounded assignments when the prior assignment is classified, the worker is resumable and idle, the project, checkout, trust boundary, authority envelope, role, and model/effort fit remain compatible, and no ownership overlaps another active worker. A fresh invocation for a later task may reuse such a worker in the same Sol session; invocation does not carry across tasks, but worker identity may. Compaction is expected and is not by itself a reason to recycle.
2. Before each new assignment to a reused worker, send the complete Compact Luna Worker Contract with an assignment-reset overlay naming the prior assignment ID and disposition, facts that may carry over, and assumptions, scope, permissions, decisions, or completion claims that must not carry over. Restate every applicable contract field for the new assignment, including interfaces, success criteria, and return format. Old scope, permissions, decisions, and completion claims do not carry forward unless restated. Require the worker to surface any stale or conflicting inherited assumption before acting. A bounded correction within the current assignment needs only the changed constraint, not a full reset.
3. Keep one owner per workstream, not disposable workers per operation. Reuse one worker for sequential dependent work, never assign one worker concurrently to multiple workstreams, and track both worker identity and workstream identity so reuse does not erase earlier status or evidence. Parallel work still requires the ownership and handoff boundaries above.
4. Stop reusing an implementation worker and create a fresh one when the repository, checkout, trust boundary, authority, or permission envelope materially changes; its model or effort conflicts with the Luna setting in force for this lens (`gpt-5.6-luna` at xhigh by default, or the operator's explicit override); the worker continues to act on a superseded contract after a reset restated the current one; a decision-critical constraint lost during compaction cannot be restored reliably through a reset; the worker repeats an acceptance-critical miss, stale assumption, or over-engineered direction after correction; unresolved prior state would be hidden by reuse; the worker cannot be resumed; or the operator explicitly requests a new worker. When an expected worker identity is unreachable or cannot resume, report the lost continuity and prior disposition before creating a fresh worker; do not present the replacement as reuse. For independent acceptance review, keep the implementation worker available for fixes and use the Sol reviewer lane below.
5. Do not create or recycle a worker merely because a task, workstream, or assignment boundary was crossed, or on a fixed count, token budget, or elapsed-time schedule. Small adjacent assignments should not create disposable workers; a large ongoing workstream does not protect an unhealthy or incompatible worker from recycling. Needing an additional independent owner adds a worker; it does not recycle a healthy compatible owner. Routine corrections, verification, rerouting, a delayed handoff, or a new operator decision within the same authority envelope are not sufficient by themselves. Do not duplicate a handoff or replace a worker merely because delivery is delayed while the worker remains active.
6. Keep implementation and review identities separate. Never turn an implementation worker into its own reviewer; use the persistent Sol reviewer lane below.
7. Continuity is a context optimization, not authority or acceptance. Reusing a worker across tasks requires a fresh explicit invocation and assignment reset; it never expands permissions, bypasses a stop gate, or weakens Sol's independent gate.

## Conditional Independent Sol Review

1. The primary Sol's narrow independent gate is always required. An explicit operator or governing-driver request always requires the independent Sol reviewer. Otherwise use the reviewer when at least one condition makes independent judgment plausibly acceptance-changing: consequential architecture, public-interface, migration, security, privacy, permission, destructive-data, scientific-validity, release, or GPU risk; multi-worker integration whose correctness depends on a cross-worker handoff or contended shared mutable state beyond the common checkout; conflicting or materially incomplete evidence; unresolved acceptance-critical uncertainty; or substantial primary-Sol judgment that creates anchoring risk. For these risk-triggered reviews only, skip the reviewer for a routine, reversible, bounded change whose identified risks are resolved by deterministic checks and leave no material judgment.
2. Reuse one compatible, idle Sol reviewer whenever its native identity remains reachable from the current Sol session. If none exists, create it as a Sol subagent lane with fresh context and no inherited parent Sol conversation or implementation conversation using the Sol model identifier exposed by the running product (currently `gpt-5.6-sol`) at high effort. Apply the no-parent-history launch and confirmation rule from Decompose And Route 6 with no bounded-history exception for a new reviewer; if the product cannot set or confirm it, stop and ask the operator before dispatch. The operator-requested ordinary Luna task/thread route does not change the reviewer route. Use another value or reviewer route only when the operator explicitly requests it. Before each review dispatch, state whether the reviewer is reused or new and name its route, Sol model, and effort.
3. Dispatch no review packet until implementation is integrated, the checkout is quiescent, the primary Sol has inspected the actual accumulated diff, and required verification is complete. Keep the checkout quiescent for the entire review; any primary-Sol or worker mutation during that window invalidates the review and requires integration and verification again before a new packet. Send a review packet containing the review ID; user's current goal; exact accumulated change set or revisions; interfaces, constraints, and nonclaims; evidence locations and permitted non-mutating inspection commands; material risks and uncertainty; acceptance criteria; return route; required review result format; and explicit read-only, no-mutation, no-delegation instructions that keep the reviewer a leaf. State-writing test, build, or generation commands must be completed by Sol before dispatch or, when reviewer execution is necessary and authorized, run in isolated scratch state outside the reviewed checkout. For a reused reviewer, add the prior review ID, disposition (`ship`, `fix-first`, `rethink`, `blocked`, `failed`, or `voided`), and reviewed state. Explicitly invalidate any prior verdict and carry forward only confirmed project invariants and still-relevant findings. Separate raw evidence from any primary-Sol interpretation and require the reviewer to inspect the actual files, artifacts, and complete current diff before reading that interpretation, not only changed fixes, summaries, or worker reports.
4. When evidence is sufficient, require `ship`, `fix-first`, or `rethink`, with a decisive reason, precise findings, and residual risk. When the reviewer cannot complete the review or lacks required evidence, require `blocked` with the reason, missing inputs, and current review state; `blocked` is not a verdict. `Failed` means the review dispatch terminated without a verdict or `blocked` report; it supplies no review evidence, so re-dispatch to the same compatible reviewer when reachable or recycle an unreachable reviewer. Treat read-only isolation as enforced only when the running product reports it; under a broader policy, proceed only when hard isolation is unnecessary, capture exact before/after state, and report the residual risk. Non-mutating inspection is allowed; reviewer changes to the reviewed checkout or other durable state void the review result. Discard the verdict, report the mutation, and recycle the reviewer. Restore affected state only within existing authority; if the mutation cannot be fully reverted, stop and escalate to the operator. Re-establish and reverify the integrated diff baseline before any new review packet or acceptance. A voided review is not a finding against the implementation.
5. Classify every review dispatch as verdict delivered, blocked, failed, or voided. When independent review is required, withhold acceptance until Sol resolves the disposition and receives a valid verdict or the operator explicitly waives the review; a failed dispatch must be re-dispatched or explicitly waived. The reviewer's verdict is evidence, not acceptance; the primary Sol adjudicates it. Send `fix-first` corrections to the original implementation worker when resumable, then integrate and verify again. `rethink` returns architecture and scope decisions to the primary Sol. Any changed implementation state invalidates the prior verdict, but not the reviewer identity; send a new review packet with the reuse-reset fields when review remains required.
6. Treat the Sol reviewer as a persistent independent lane, not a disposable worker. After each review dispatch or classification change, restate the reviewer identity, reuse status, last review ID, last disposition, and reviewed state in the visible Sol session state; this is the recovery point across compaction and the source for the next review-reset packet. Reuse the reviewer across fixes and later tasks in the same compatible repository, checkout, trust boundary, authority envelope, and Sol session; never assign concurrent reviews. Compaction, task boundaries, elapsed time, prior `fix-first`, and prior `ship` verdicts are not recycle triggers. Recycle the reviewer only when its native identity is unreachable; its model or effort conflicts with the reviewer setting in force for this lens (`gpt-5.6-sol` at high by default, or the operator's explicit override); the repository, checkout, trust, authority, or isolation boundary changes; it mutates state or assumes implementation ownership; a review reset cannot correct stale or anchored conclusions; it repeatedly misses an acceptance-critical issue; or the operator requests a fresh reviewer or genuinely independent second opinion. One healthy reviewer may persist for the lifetime of the compatible Sol session.

## Operator-Requested Thread Route

1. Obtain the originating Sol session ID from the native current-task identity or status surface. Do not invent an ID or create a side-channel file for it.
2. State that the operator requested an ordinary Luna task/thread. Use the Luna model identifier exposed by the running product (currently `gpt-5.6-luna`) at xhigh unless the operator explicitly requests another value. State the model and effort before launch.
3. Apply Decompose And Route 1–3 to this route as well. Create the Luna task/thread with the compact worker contract, including the exact originating Sol ID as its return route. Do not change the originating Sol session's model or create a worktree without operator approval.
4. After launch, satisfy any checkpoint requirement the driver already imposed, but do not create a checkpoint solely for this lens. Immediately return one concise launch response line for each Luna task/thread actually launched. Do not wait, poll, or emit no-op progress messages after launch. Dispatch a dependent lane only when its upstream assignment is classified complete in the originating Sol session and Sol validates the final handoff; do not poll to discover it. Each Luna task/thread reports only a blocker or final handoff to the originating Sol session through the native continuation mechanism.
5. Reuse the same Luna task/thread for compatible successive assignments after sending the assignment-reset contract. For a later task, reuse it only after the operator explicitly invokes this lens again and requests the ordinary task/thread route again. Create a new task/thread when the operator explicitly asks for one or a recycle trigger applies. If the operator asks for status or resumes after an expected report did not arrive, perform one native status/read check; re-send the contract only when the task is idle or ended without delivering it, and never duplicate delivery or launch a replacement silently.

## Compact Luna Worker Contract

Send only the minimum sufficient contract. Include conditional fields only when they apply; omit them instead of filling them with boilerplate:

- **Objective:** the concrete bounded outcome.
- **Durable references:** relevant task, spec, source, and instruction paths; point to files instead of pasting their contents.
- **Scope and ownership:** files, components, or questions Luna owns plus explicit non-goals, read/write limits, and overlap boundaries.
- **Interfaces:** signatures, types, schemas, commands, and behavior that must remain compatible.
- **Authority:** local write, validation, commit, push, lifecycle, and external-write permissions exactly as granted by the operator and governing project rules; delegation permission is always none because every Luna worker remains a leaf.
- **Context and continuity:** whether the worker is new or reused; assignment and workstream identity; prior assignment disposition when reused; current authoritative checkpoint; facts that may carry over; and prior assumptions, scope, permissions, decisions, and completion claims that must not carry over.
- **Dependencies and handoffs, when applicable:** required inputs, named downstream workstream or owner, expected artifact or fact, delivery condition, integration order, and Sol as the handoff recipient; the worker remains a leaf.
- **Success criteria:** observable completion conditions and required artifacts.
- **Verification:** authoritative contracts Luna must recover and cite; exact or proportional checks; expected decision-bearing evidence; plausible wrong implementations the tests must distinguish; failure and recovery paths to trace; and evidence to preserve.
- **Reviewed behavior-spine proof, only when the driver says it applies:** proof that the oracle is independent, a semantics-preserving implementation refactor remains green, a plausible production defect turns the spine red, and a detector ledger accounts for deleted or weakened tests.
- **Stop/ask gates:** architecture decisions, user-owned choices, unsafe scope expansion, missing authority, unavailable infrastructure, ambiguous or conflicting evidence, dependency failure, or other material ambiguity Luna must escalate instead of guessing.
- **Return route:** the parent Sol session for a subagent, or the exact originating Sol session ID for an operator-requested ordinary task/thread; report nowhere else.
- **Return format:** status (`complete`, `blocked`, `partial`, or `failed`); outcome; changed files or commit; verification; material judgment calls or `none`; blockers; material uncertainty; dependency handoffs; the worker's continuity state (`resumable`, `ended`, or `unable to continue`) as evidence for Sol; when decision-bearing evidence applies, a concise inspection summary naming scope, depth, load-bearing observations that support or weaken acceptance, limitations (including uninspected items and reasons), and any divergence from the expected evidence set. Sol alone decides whether to reuse or recycle.

Do not include builder reasoning, long conversation history, failed-attempt narration, or a request for hidden chain-of-thought. Send no routine progress or acknowledgement messages; send only a blocker or stop/ask escalation or the final report through the selected return route.

## Luna Worker Rules

- Recover and cite the authoritative inherited contracts before implementation; do not substitute an internally consistent interpretation for the governing definition.
- Inspect the entire final diff for owned paths and the decision-bearing artifacts the delegated claim rests on, including owned tests and generated or configuration changes, before reporting review-ready. During concurrent work, report foreign changes to Sol instead of treating them as part of the worker's verification; Sol owns the integrated full-diff and whole-suite gate.
- Cover each non-interchangeable decision-bearing artifact in the first pass; use sampling only for genuinely interchangeable items, state the sampling basis and limitations, inspect load-bearing items at proportional depth, add newly discovered decision-bearing evidence to the inspection summary, and report divergence from the expected set.
- Do not treat a producer's success signal, metadata, or contract checks as inspection of the decision-bearing artifact; examine the artifact itself when the claim rests on it.
- Run adversarial consequence tests that distinguish plausible wrong implementations, not only happy-path or source-shape checks.
- Reject an implementation-derived oracle: expected behavior must not come from production identifiers, generated keys, internal paths, or source shape unless that exact shape is the documented contract.
- Trace fail-closed, error, retry, and recovery behavior in proportion to the task's failure surface.
- Challenge the implementation and evidence against task nonclaims and report residual uncertainty explicitly.
- Keep changes within the delegated scope, respect sibling ownership, and preserve unrelated operator work.
- Escalate architecture changes, contract changes, unsafe broad rewrites, missing authority, dependency conflicts, or materially different interpretations to Sol.
- Never upgrade Luna work to Sol automatically, broaden delegation authority, or claim success when required evidence is missing.
- Report using the return format above; keep any decision-bearing inspection summary concise and omit step-by-step narration and hidden reasoning.

## Sol Token-Efficiency Rules

- Spend Sol tokens on planning, decomposition, architecture and risk decisions, dependency design, worker contract quality, integration, the narrow independent gate, and acceptance.
- Let Luna own authoritative-contract recovery, broad routine scans, line-by-line implementation, local diagnostics, adversarial verification, owned-diff and first-pass evidence inspection, and test execution needed for its bounded workstream.
- Use parallel read-only scouts or non-overlapping workers only when their outputs can change or accelerate a named downstream decision; otherwise keep one worker and avoid coordination overhead.
- Challenge load-bearing assumptions, scientific validity, and release or GPU readiness as applicable; apply the decision-critical gate defined in the Operating Model at proportionate depth, expanding only for conflicts, unexplained gaps, or acceptance-critical uncertainty, without redoing Luna's implementation-depth verification by default.
- Do not infer oracle independence from a green suite. When a reviewed behavior spine applies and it is practical, use isolated scratch state to confirm a semantics-preserving implementation refactor remains green and a plausible production defect turns the spine red.
- Treat a basic implementation or evidence fact rediscovered by Sol as Luna-handoff feedback: correct the current workstream, carry a reusable lesson into later Luna worker contracts, and propose a durable update to this skill or the governing project checklist under normal authority. Do not silently modify durable assets without authority.
- Do not poll or repeat unchanged progress. Report only state changes that matter to the operator.
