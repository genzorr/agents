# Systemic Diagnosis

Use this experimental lens only when a problem recurs, spans components or teams, survives local
fixes, or plausibly involves delayed or backfiring effects. Do not use it as a mandatory global
method, router, workflow, or swarm. An active driver remains responsible for sequencing, decisions,
actions, and the final result.

## Lens

1. Frame the outcome gap, system boundary, relevant actors, and time horizon. Use breadth before
   depth: separate the latest event from the pattern over time, then scan structure and assumptions
   before choosing one load-bearing branch to inspect deeply.
2. Map only material structure: actors or components, rules, ownership, incentives, capacity, delays,
   and causal links. Identify reinforcing or balancing loops only when evidence supports them; never
   force a diagram, loop, or single root constraint.
3. Label load-bearing claims as **observed/measured**, **inferred**, or **hypothesized**. Seek
   disconfirming evidence, keep refuted branches visible, and name the cheapest test that would
   distinguish competing explanations.
4. Separate symptom relief from mechanism change. Run candidate interventions forward far enough to
   expose likely side effects or feedback, and quarantine plausible but untested ideas as ideas rather
   than causes or recommendations.
5. State whether the result is a supported verdict or a map of what to test next. Update the map,
   claim labels, confidence, and next test incrementally when new evidence arrives; do not rewrite
   earlier uncertainty into certainty.

For a compact situational selector and progressive disclosure order, open
`docs/systemic-diagnosis-selector.md`.

## Composition boundary

Keep existing ownership: `diagnose` drives a bounded software fault; `zoom-out` maps code context;
`architecture-review` examines module and interface shape; `grill-with-docs` resolves decisions;
`design-experiment` freezes an empirical test; and `prepare-dynamic-workflow` handles branch-space
or independent refutation that exceeds one context. This lens adds questions and evidence discipline;
it never takes lifecycle ownership or relaxes another skill's protocol.
