# Review checks

Open this reference for a code/change review; apply only checks relevant to the resolved target.


- **Correctness**: wrong conditions, stale assumptions, broken invariants, off-by-one errors, bad async/order behavior, incorrect state transitions, data loss.
- **Requirements**: mismatch with user request, task acceptance criteria, docs, API contract, or PR intent. A clean, well-tested implementation of the wrong or narrowed target is still a requirements failure — flag it even if the diff itself is high quality.
- **Edge cases**: empty/null inputs, boundary sizes, malformed external input, retries, concurrent operations, partial failures.
- **Security and privacy**: authz/authn gaps, secret leakage, injection, path traversal, unsafe deserialization, excessive logging, PII exposure.
- **Performance**: avoidable N+1 queries, unbounded loops, repeated expensive work, cache invalidation, large memory spikes, slow startup/build paths.
- **Interfaces**: breaking API changes, migration gaps, inconsistent names/types, confusing return values, missing compatibility handling.
- **Maintainability**: over-engineering, duplicated logic, unnecessary abstractions, hidden coupling, complex code where a simpler local pattern exists.
- **Deliberate simplification**: after a substantial change, identify assumptions, states, branches, wrappers, or repeated knowledge that could be removed within scope while preserving requirements. Check the whole path for hidden rules pushed into callers; fewer lines alone do not establish improvement. A no-change conclusion is valid; flag only concrete task-related opportunities.
- **Current guidance**: derive affected owners from changed behavior and decisive evidence, including relevant guidance absent from the diff. Changed documented commands, contracts, prerequisites, ownership boundaries, recovery paths and workarounds must be reflected in their current authoritative docs in the same change. Pending adoption or future improvements do not waive known misleading guidance for the delivered supported path; qualify affected reliance and name the responsible follow-up when correction or proof is outside scope. Preserve historical evidence, distinguish superseded guidance, and remove workarounds whose cause disappeared; do not demand a new instruction for every completed task.
- **Reuse-before-build**: new code, helpers, CLIs, abstractions, dependencies, or skills that skipped an obvious lower rung — existing repo pattern/tool, standard library, native platform/framework capability, existing dependency, or config/flag/rule change.
- **Verification**: missing or weak tests for risky behavior, tests that do not exercise the changed contract, CI gaps, and decision-locking assertions that pin a legitimately changeable value, relationship, text, or source shape without naming a production defect and observable consequence. Exact assertions remain valid when the exact value, text, or shape is itself a documented public, safety, compatibility, or shipped-artifact contract.
- **Reviewed behavior spines**: when the change claims a reviewed executable behavior authority, verify that implementation did not weaken it; its supported public seam, controlled boundaries, independent oracle, prohibited shortcuts, and claim ceiling are explicit; adequate existing proof is reused; and every deleted or weakened test's detector is accounted for in the existing task/review account, with evidence of remaining protection. Where scenario adequacy is uncertain, verify a legitimate implementation change remains green and a plausible production defect turns it red; reuse applicable challenge evidence rather than require a mutation exercise on every edit. Use the existing account rather than create a parallel detector ledger. Preserve meaningful regression proof and independently applicable project requirements. Do not infer oracle independence from a green suite: expected behavior derived from production identifiers, generated keys, internal paths, or source shape is implementation-derived unless that exact shape is a documented contract. When needed and practical, run those challenges in isolated scratch state.
- **Semantic fidelity**: when the change implements a source or paper, claims a behavior-preserving refactor, or transforms data whose meaning must survive, verify that it names the authoritative source or behavior, preservation obligations, and forbidden approximations, proxies, lossy shortcuts, or unsupported substitutions. When an ordinary happy-path test could accept a plausible semantic shortcut, require discriminating proof—such as a counterexample, differential oracle, round-trip property, or adversarial fixture—that would reject it. Treat missing authority or proof as a finding only when semantic fidelity is material to the claimed outcome.


## Reader tasks and reference closure

When documentation changes or supports the delivered behavior, follow one representative reader task from its entry. Can the reader find the right spec, predict a boundary/failure, run the supported check and update connected guidance without private discussion? A link-correct page can still fail by omitting a prerequisite or leaving the next action unexplained. Report the failed task and concrete consequence, not a style preference.

For a claimed portable bundle, copy exactly the documented set and follow operative code-formatted dependencies as well as Markdown links. Distinguish actual read requirements from illustrative filenames, provider mechanics and explicitly optional assets. A reference available only in the author’s checkout does not establish portable closure.
