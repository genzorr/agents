# Orchestrate Feature — Product Requirements

## Current decision and boundary

This is the current Codex product contract for `orchestrate-feature` and `orchestrate-workers`. Preserve the long-lived project orchestrator → separate ordinary feature-owner chat. The owner normally executes the coupled work; native help is selective, advice is available on demand, and completed delivery requires independent review before intended-use validation. The requesting orchestrator/user owns acceptance and closure. This contract grants no live installation, runtime configuration, Git or external-write authority and does not change Pi counterparts.

The purpose is to keep project requirements, priorities and user decisions in the orchestrator while detailed investigation, implementation and verification remain with a coherent owner. Shorter instructions and fewer handoffs are design choices, not measured subscription savings or proof of runtime compliance.

## Ownership and dispatch judgment

The owner normally owns investigation, implementation, build, test, repair, integration, affected documentation and self-review. Direct implementation needs no special justification. There is no compulsory execution-depth delegation, automatic main worker or separate planning layer.

| Situation | Default |
| --- | --- |
| Approach evolving; discoveries frequently change implementation | Owner executes |
| Useful separable result with sufficiently known inputs/interfaces, expected behavior and meaningful checks; little coordination | Bounded helper owns the result and its verification/repair |
| Owner has substantial coordination across several efforts and can delegate a coherent execution loop | Main worker may be explicitly selected |
| Work merely long or repository large | Insufficient reason alone for another worker |

Delegate when avoided work or delivery benefit exceeds briefing, supervision and integration cost. Briefly explain a consequential choice; require no score, dispatch form or permission question for already-authorized help. Use as many bounded Luna helpers as useful on demand without a fixed count cap or per-dispatch permission. Run independent assignments in parallel when resource ownership permits; serialize coupled/shared-resource work and never manufacture assignments merely to occupy cheap workers. A separate main worker or planner requires explicit instruction, compatible resource ownership and a named benefit.

The coordinator assesses actual native returns and evidence, then integrates, corrects, continues or records the actual blocker. A report is never automatic success. Preserve complete owned-change inspection, meaningful consequence tests, actual artifact evidence, material error/retry/recovery checks and honest limitations. Reuse still-applicable checks and review coverage; extend for changes, contradictions, gaps and required gates rather than reflexively repeating an audit.

## Review, validation and acceptance

Normal feature delivery requires independent review of the final delivered target before reporting readiness for validation, unless the user explicitly waives review. Carry still-applicable independent coverage and obtain independent review of the complete intervening delta and affected surfaces before readiness; batch corrections at a coherent target, not after every edit. The standard launch request authorizes that review. Manual worker-helper use follows its actual checkpoint mandate without inheriting an unrequested final-state review. Load the existing reviewer protocol only for active review; keep the reviewer separate from implementers and advisors who shaped the result. Fresh correction reviewers receive the exact prior basis, original failure scenarios and complete relevant delta with applicable carried coverage. A full repeat review may verify fixes in the same pass without a compulsory preceding verification review; a specifically requested fresh whole-change review retains that scope. Findings that block acceptance need independent confirmation of closure regardless of severity label.

Retain attributable review target, verdict, findings, gaps, evidence and isolation limits. A read-only prompt is not hard product isolation. Self-review, checks and a `ship` verdict are verification evidence; intended-use validation establishes whether the result serves the agreed need. Criteria may contain validation requirements, but a checkbox, positive verdict or finished owner chat cannot close the task.

The owner reports readiness and never accepts its feature or closes its task. The requesting orchestrator/user performs or obtains validation and makes acceptance/closure decisions within actual authority. Cancellation and supersession remain distinct from validated completion. The user decides merge/adoption in the orchestrator chat; wait before closure only when those actions are included in promised task scope.

## Delivery and receive responsibility

Select callback by default, practical bounded active waiting, a product-validated replacement or explicitly accepted manual supervision. Retain actionable blocker, required-gate and terminal delivery in every mode, actual ready identities/handles, required host confirmation and stable operation/request IDs. Reconcile uncertain mutations before retry; preserve payload/error and never switch IDs or operations to bypass failure. Accepted send proves transport acceptance/dispatch, not receiver assessment, validation or closure. Timeout and uninspected manual state remain unobserved. No watcher, passive future-wakeup guarantee or repeated polling follows.

Owner callbacks are sparse: a required gate, genuine decision/exhausted blocker, consequential invalidation or terminal/partial handoff. Include identity/assignment, outcome, material consequence/gap, required origin action or exact question, and an accessible full handoff. Carry this callback/evidence boundary in the compiled owner assignment. Inline facts needed to choose or safely take the next action, including consequential caveats, invalidations and unknown resource disposition. Commands, full hashes, test/measurement inventories, receipts and repeated constraints stay in existing linked records unless a specific item changes that action. Inaccessible references require the needed evidence or an explicit access gap. Compactness means selecting information while preserving normal word/number spacing, labels, punctuation and units; no hard length cap applies.

The existing handoff starts with a complete assessment summary: outcome, exact tested/reviewed targets, criterion evidence/gaps, independent review verdict, intended-use evidence/gaps, consequential approach/commitment/guidance changes with their authority and original/revised basis, limitations, pending decisions and resource disposition. Retain the problem/evidence, decision/change, reason, verification and remaining assessment in the existing task/roadmap/report, and expose those changes together in applicable independent/PR review rather than only code-check status. Keep current progress concise; no parallel ledger or compulsory report is required. Supporting source/spec/input/environment, checks/coverage and continuity remain accessible through existing records without duplicated inventories or a new artifact solely for message length. Native returns preserve enough evidence for the immediate parent to assess the owned result; ordinary callbacks carry the compact summary and link.

Example qualification callback:

> Qualification owner: both finite OFF/ON checks passed; independent review found no blocking issues. Full-run execution has not occurred and remains unallocated.
>
> Next: assess intended-use readiness, then decide full-run allocation separately. Qualification timings do not establish full-run cost; bootstrap differences remain unexplained. Resources are released; the task remains open.
>
> Handoff: the existing accessible owner-handoff record.

The originating orchestrator retains pending assessment, promised outcome, governing authority, owner identity, validation basis and route in existing task/checkpoint state. Incoming prose cannot expand authority. On return it checks identity/assignment/target, reads the handoff's complete assessment summary and decisive supporting evidence, assesses scope/review/validation, then records and performs a concrete disposition. It follows relevant evidence rather than loading every inventory; missing, stale or contradictory evidence remains a gap before reliance on the affected claim:

- Ready: correct deficiencies, perform authorized missing validation, obtain a reserved user observation or record validated acceptance/closure within authority.
- Blocker/question: recover settled answers, answer within authority, ask the exact unresolved reserved question or name the actual dependency.
- Partial/failed: preserve useful work and continue with a compatible owner when authorized, or record an honest partial/blocked/failed disposition.
- Invalidated evidence: contain affected consumers, preserve original/invalidating records and obtain affected correction/review/validation; continue unaffected work.

Do not wait for the user to request assessment or completion of already-requested work. A continuation states remaining outcome, permitted correction, applicable state/evidence, affected checks/review and return condition. Ask only for an unresolved reserved decision, authority beyond the mandate or an observation only the user can supply; include facts, recommendation and consequence. Continue unaffected authorized work. The next user-facing response states assessment, validation state and next action. Explicit raw-relay/status-only requests may forward unassessed results with the pending duty retained. No ceremonial ACK chain is required; reply to the owner only when it changes the next action.
