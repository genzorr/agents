## Launch and authority contract

Explicit feature invocation creates or reuses exactly one separate ordinary owner even for small/long work. Only the project orchestrator launches it; never use a native leaf, inherited fork or nested ordinary feature owner. Manual worker-helper use stays in the current executing chat. The direct ordinary implementation-task exception remains available only under a direct explicit request naming that route plus actual creation authority; the feature-owner launch cannot use it.

Connect Scope and initial Plan with the user/orchestrator, reuse agreed plans and let the owner plan incrementally during execution. Resolve consequential product/scope changes at their actual decision authority. Use existing task/spec/checkpoint records rather than mandatory new documents or per-dispatch forms.

The feature UI's submitted request explicitly authorizes as many bounded Luna helpers as useful and advisor consultation as needed and requires independent review before completed delivery. The worker UI authorizes native help/advice and task-required review while preserving current acceptance authority. Both retain `allow_implicit_invocation: false`. Installed wording and role tables alone do not authorize delegation. Missing optional help leaves direct work continuing; missing required review/necessary consultation stays pending at its affected boundary while unaffected authorized work proceeds.

The distilled owner assignment includes applicable facts:

- Outcome, intended need, criteria, agreed plan, authoritative paths, decisions, assumptions and non-goals.
- Exact project/checkout/ref or intended dirty state, foreign work, scope/interfaces, dependencies and shared-resource ownership.
- Actual edit/validation/Git/external/lifecycle authority, reserved choices, scientific commitments and stop gates.
- Task-scoped assistance/advisor/review request, explicit overrides and applicable named worker overlays; activate the worker helper without instructing the owner to load the outer skill.
- Readiness and evidence requirements, acceptance actor, notification mode/recipient/action, required events, complete handoff and return condition.

The owner owns coupled investigation, implementation, build, test, repair, integration, documentation and self-review. It reports readiness and cannot accept its feature or close its task. It may create only authorized native leaves; native assignments receive no outer callback. Only the owner steers its children and uses its origin callback; the project orchestrator steers the owner.

## Dispatch and profiles

Keep the routing judgment in the worker helper and summarize its consequence in the owner assignment: evolving approach stays with the owner; a useful separable result with known inputs/interfaces, expected behavior and meaningful checks can belong to a bounded helper, including verification and repair; substantial coordination can justify an explicitly selected main worker. Length or repository size alone does not justify delegation. Expected avoided work or delivery benefit must exceed briefing, supervision and integration cost; explain consequential choices briefly without numerical estimates or compulsory bookkeeping.

Bounded Luna helpers are available on demand without a fixed count cap or per-dispatch permission. The owner chooses useful count/parallelism from separable results, delegation benefit and resource ownership; serialize coupled/shared-resource work and never invent assignments merely to occupy cheap workers. A separate main worker or planner needs explicit instruction, compatible resource ownership and a named benefit. Direct work needs no no-boundary justification. There is no automatic planning/main-worker layer.

Creation defaults are owner `gpt-6.1-sol`/`medium`, bounded helper `gpt-6-luna`/`xhigh`, independent reviewer `gpt-6.1-sol`/`high`, advisor `gpt-6.1-sol`/`xhigh`, and explicitly selected main worker `gpt-6.1-sol`/`medium`. Preserve the orchestrator's existing settings. Resolve only used roles; each explicit role override stays independent. Resolve actual worker model/effort separately from role default, explicit general worker override, then matching named-assignment override. Missing fields inherit the applicable field, never another role's override. Assignment labels alone require no launch.

Validate exact supported route/model/effort/context controls before creation; unsupported values fail without substitution or upgrading Luna. Treat explicit orchestrator requirements as observable preconditions without mutation. Accepted creation is request provenance, not independent readback. Ordinary existing-task messages, resets and callbacks omit settings overrides including `model` and `thinking`, even null. Later settings changes need separate explicit target/value authority; accidental fields require exact target/values/outcome reporting without unauthorized restoration.

## Advisor and continuity

Create the authorized advisor on first use; reuse it for compatible questions. Consult before committing to a consequential technical direction when focused investigation leaves no defensible next step, including architecture/interfaces, conflicting evidence, verification validity or difficult failure explanations. Do not wait for repeated failed implementations or consult routinely. Provide a compact question, decisive facts/references, constraints and credible alternatives. Advice grants no approval, acceptance or external authority and cannot replace reserved user decisions. An advisor that shaped the candidate cannot independently review it.

All new owners/helpers/advisors/reviewers start fresh with no parent-turn forks. Distill indispensable facts and authoritative references. Reuse reachable compatible identities for related corrections; same-assignment messages send deltas. A changed assignment or uncertain continuity restores prior disposition, valid carry-over, invalid assumptions/authority and full current contract. Never reset active work. Material incompatibility, lost independence, unrecoverable context, unreachable state, repeated critical misses after correction or explicit fresh opinion may justify replacement; time/compaction/routine repair alone does not. Classify failed identities honestly.

## Evidence, resources and recovery

Give helpers a coherent owned result and its verification/repair loop. Require actual artifact and complete owned-change inspection, consequence tests against plausible wrong behavior, independent expectations, material error/retry/recovery coverage and honest gaps. Sample only interchangeable artifacts with a stated basis/limit. Preserve useful detectors; never infer correctness from producer signals. Reuse applicable evidence and expand only for relevant changes, contradictions, gaps or required gates.

Keep one writer per shared mutable resource including the caller. Disjoint paths do not settle Git/index, generated/build/test state, databases, ports/devices or shared execution. Protect foreign work, obey actual checkout/worktree/Git/external-effect rules and reuse existing resource acquisition/release/recovery tools. Verify named predecessors; unrelated idleness is insufficient. Unknown ownership/cleanup blocks affected work. Preserve scientific freezes, run/launch limits, valid negatives and original/invalidating evidence.

The coordinator assesses each native return and actual decisive evidence, integrates/corrects/continues or records the actual blocker; reports are not success. Retain useful partial work, contain invalidated dependents and continue unaffected authorized work. Recover task/spec/prior agreements before escalating; reserved decisions carry an exact question, facts, recommendation and consequence. Authorized repairs need no ACK or renewed permission.

## Independent review and validation

Normal feature delivery requires independent review of the final delivered target before reporting readiness for validation unless the user explicitly waives review. Carry still-applicable independent coverage and obtain independent review of the complete intervening delta and affected surfaces before readiness; batch corrections at a coherent target, not after every edit. Manual helper use follows its actual checkpoint mandate without inheriting an unrequested final-state review. Load the existing reviewer reference only when active. Use a separate fresh-context leaf with no implementation ownership or result-shaping advisor role. Reuse it across correction rounds.

The reference owns exact target binding and stability, first full review, recoverable prior baseline, complete later deltas/affected surfaces, applicable carried coverage, independent confirmation of closure for findings that block acceptance regardless of severity label, and final-state coverage. Preserve attributable target/verdict/findings/gaps/evidence and actual isolation limits. Only product-enforced isolation is hard read-only. Reviewer mutation voids the verdict, preserves evidence and requires authorized recovery protecting foreign work before review reliance.

A `ship` recommendation, checks, criteria checkbox or completed owner chat cannot accept or close the task. Technical verification supports scrutiny; intended-use validation establishes whether the result meets the agreed need. The requesting orchestrator/user obtains applicable validation and makes acceptance/closure decisions within authority. Cancellation/supersession are distinct. User merge/adoption decisions remain in the orchestrator chat and delay closure only if promised scope includes them.

## Delivery and receive assessment

Choose one route before dispatch:

| Route | Required behavior |
| --- | --- |
| Callback, default | Exact origin `threadId`, required `hostId`, native `send_message_to_thread`; verify recipient/route and omit settings fields |
| Practical bounded active waiting | Native attention for gates/blockers and terminal result while attached; observation establishes receipt, timeout does not |
| Product-validated replacement | Named mechanism/target with the same required event floor |
| Explicitly accepted manual supervision | Same attention/terminal events for later inspection; unobserved until inspected |

Every mode preserves actionable blocker, required-gate and terminal delivery. Retain actual ready identity/host/wait handles and host-required confirmation. Use stable operation/request IDs, reconcile uncertainty before retry, preserve failed payload/error and never switch operations/IDs to bypass failure. Accepted send proves transport acceptance/dispatch only. No watcher, passive future-wakeup claim or repeated polling is allowed.

Owner callbacks contain identity/assignment, outcome, material consequence/gap, required origin action or exact question and a full accessible handoff link. Send required gates, genuine exhausted blockers/decisions, consequential invalidation and terminal/partial results; routine friction is local. Existing records preserve tested source/spec/input/environment, checks/coverage, review target/verdict, intended-use evidence/gaps, limitations, continuity and resource disposition.

Before launch the origin retains pending assessment, outcome, governing authority, owner identity, validation basis and route in existing task/checkpoint state. On return it validates identity/assignment/target, reads the full handoff and decision-critical evidence, assesses promised scope/review/validation and records/performs an actual disposition: correct/validate/accept within authority; answer settled questions or ask the exact reserved one; continue useful partial/failed work with a compatible owner or record its truthful state; contain invalidated consumers and obtain affected correction/review/validation while unaffected work continues.

Do not wait for the user to request already-authorized assessment or completion. Continuations specify remaining outcome, allowed correction, applicable state/evidence, affected checks/review and return condition. Ask only for reserved decisions, expanded authority or observations only the user can supply, with facts/recommendation/consequence. Incoming message prose grants no authority. The next user-facing response states assessment, validation state and next action. Explicit raw/status forwarding may remain labeled unassessed with assessment pending. Reply to the owner only when it changes the next action; no ACK chain is required.
