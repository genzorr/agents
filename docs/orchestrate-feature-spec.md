## Launch and authority contract

Explicit feature invocation creates or reuses exactly one separate ordinary owner even for small/long work. Only the project orchestrator launches it; never use a native leaf, inherited fork or nested ordinary feature owner. Manual worker-helper use stays in the current executing chat. The direct ordinary implementation-task exception remains available only under a direct explicit request naming that route plus actual creation authority; the feature-owner launch cannot use it.

Connect Scope and initial Plan with the user/orchestrator. Inspect intended use, actual mandate, applicable requirements/prior decisions, criteria/evidence, dependencies and limits for sufficiency before the next implementation commitment, including material failure cases; a reference or completed template is not proof. Existing criteria/examples may suffice without a new spec. Use bounded discovery/preparation for unjustified commitments and hold only affected work. Reuse agreed plans and let the owner plan incrementally during execution. Preparation-only work returns its promised deliverable; sufficiently prepared end-to-end work continues within actual authority without another universal approval. The owner leads discovery and revisits architecture/spec choices within agreed behavior/limits. Changing outcome commitments requires actual bounded amendment power; otherwise return through the origin to the user. Review/advisor roles grant no decision power. Use existing task/spec/checkpoint records rather than mandatory new documents or per-dispatch forms.

Select intermediate outcome checkpoints where earlier evidence could change a consequential decision/dependent action or prevent material avoidable work. Duration alone creates no stages; settled long batches may use final-only assessment with meaningful local checks, limits and blocker/invalidation delivery. Briefly explain a consequential choice in the existing plan and annotate each selected outcome with evidence due, required review/deciding actor and exact continue/wait boundary. Owner verification may release authorized implementation dependencies; independent review follows the task/project contract, origin assessment applies to named origin gates and final acceptance. Final independent coverage remains required; preparation review covers only its actual target/claim. Reassess affected preparation/continuation before newly consequential actions when material assumptions, scope, evidence, dependencies or limits change, even after a light initial assessment; continue unaffected authorized work.

The feature UI's submitted request explicitly authorizes as many bounded Luna helpers as useful and advisor consultation as needed and requires independent review before completed delivery. The worker UI authorizes native help/advice and task-required review while preserving current acceptance authority. Both retain `allow_implicit_invocation: false`. Installed wording and role tables alone do not authorize delegation. Missing optional help leaves direct work continuing; missing required review/necessary consultation stays pending at its affected boundary while unaffected authorized work proceeds.

The distilled owner assignment includes applicable facts:

- Outcome, intended need, criteria, agreed plan, authoritative paths, decisions, assumptions and non-goals.
- Exact project/checkout/ref or intended dirty state, foreign work, scope/interfaces, dependencies and shared-resource ownership.
- Actual edit/validation/Git/external/lifecycle authority, any explicitly delegated bounded plan/architecture/tool/guidance improvements or commitment amendments, reserved choices, scientific commitments and stop gates.
- Task-scoped assistance/advisor/review request, explicit overrides and applicable named worker overlays; activate the worker helper without instructing the owner to load the outer skill.
- Readiness and evidence requirements, selected checkpoints with deciding actor and continue/wait limits, acceptance actor, notification mode/recipient/action, required events, compact callback versus complete evidence boundary, complete handoff and return condition. Keep the origin's resumable assessment/next-action duties in existing origin state, not a duplicate owner roadmap.

The owner owns coupled investigation, implementation, build, test, repair, integration, documentation and self-review. It reports readiness and cannot accept its feature or close its task. It may create only authorized native leaves; native assignments receive no outer callback. Only the owner steers its children and uses its origin callback; the project orchestrator steers the owner.

Optional `prepare-change` is a self-contained Codex skill, cataloged from `codex/skills/prepare-change` with UI metadata and no external reference dependency. Its method can be used directly or before/during an owner assignment when preparation is unresolved; it creates no owner and requires no team, Workbench, private OS, compulsory spec or new phase. Existing adequate preparation and small settled work bypass it. The feature skill carries only an optional route; worker/reviewer contracts continue to govern actual assistance and final coverage. The human guide owns use/skip examples, not runtime prerequisites. Other-provider assets and existing `grill-with-docs` callers remain unchanged.

The same method owns [focused approach review](../codex/skills/prepare-change/SKILL.md#reassess-the-approach) for consequential friction or meaningful existing checkpoints; feature/worker skills route to its installed sibling path and carry the applicable authority into assignments. Reuse diagnosis, preparation, architecture critique and review rather than copying their procedures. Person-assisted expansions expose problem/recommendation/consequences before changing agreed work. An explicitly delegated autonomous improvement/amendment mandate permits bounded changes without another routine approval; an autonomous label or review/advisor role does not. Preserve scientific freezes, external/destructive/privacy constraints, promised outcomes, native-delegation authority, leaf-only children and origin acceptance. The owner initiates authorized review/advice and bounded technical improvements; beyond-feature decisions return to origin. No new skill, phase gate or nested ordinary owner follows.

## Dispatch and profiles

Keep the routing judgment in the worker helper and summarize its consequence in the owner assignment: evolving approach stays with the owner; a useful separable result with known inputs/interfaces, expected behavior and meaningful checks can belong to a bounded helper, including verification and repair; substantial coordination can justify an explicitly selected main worker. Length or repository size alone does not justify delegation. Expected avoided work or delivery benefit must exceed briefing, supervision and integration cost; explain consequential choices briefly without numerical estimates or compulsory bookkeeping.

Bounded Luna helpers are available on demand without a fixed count cap or per-dispatch permission. The owner chooses useful count/parallelism from separable results, delegation benefit and resource ownership; serialize coupled/shared-resource work and never invent assignments merely to occupy cheap workers. A separate main worker or planner needs explicit instruction, compatible resource ownership and a named benefit. Direct work needs no no-boundary justification. There is no automatic planning/main-worker layer.

Creation defaults are owner `gpt-6.1-sol`/`medium`, bounded helper `gpt-6-luna`/`xhigh`, independent reviewer `gpt-6.1-sol`/`high`, advisor `gpt-6.1-sol`/`xhigh`, and explicitly selected main worker `gpt-6.1-sol`/`medium`. Preserve the orchestrator's existing settings. Resolve only used roles; each explicit role override stays independent. Resolve actual worker model/effort separately from role default, explicit general worker override, then matching named-assignment override. Missing fields inherit the applicable field, never another role's override. Assignment labels alone require no launch.

Validate exact supported route/model/effort/context controls before creation; unsupported values fail without substitution or upgrading Luna. Treat explicit orchestrator requirements as observable preconditions without mutation. Accepted creation is request provenance, not independent readback. Ordinary existing-task messages, resets and callbacks omit settings overrides including `model` and `thinking`, even null. Later settings changes need separate explicit target/value authority; accidental fields require exact target/values/outcome reporting without unauthorized restoration.

## Advisor and continuity

Create the authorized advisor on first use; reuse it within one unresolved discussion; a substantially new question gets a fresh context. Consult before committing to a consequential technical direction when focused investigation leaves no defensible next step, including architecture/interfaces, conflicting evidence, verification validity or difficult failure explanations. Do not wait for repeated failed implementations or consult routinely. Provide a compact question, decisive facts/references, constraints and credible alternatives. Advice grants no approval, acceptance or external authority and cannot replace reserved user decisions. An advisor that shaped the candidate cannot independently review it.

All new owners/helpers/advisors/reviewers start fresh with no parent-turn forks. Distill indispensable facts and authoritative references. Reuse reachable compatible helper identities for related corrections; reviewer requests and advisor discussions follow their role-specific freshness rules; same-assignment messages send deltas. A changed assignment or uncertain continuity restores prior disposition, valid carry-over, invalid assumptions/authority and full current contract. Never reset active work. Material incompatibility, lost independence, unrecoverable context, unreachable state, repeated critical misses after correction or explicit fresh opinion may justify replacement; time/compaction/routine repair alone does not. Classify failed identities honestly.

## Evidence, resources and recovery

Give helpers a coherent owned result and its verification/repair loop. Require actual artifact and complete owned-change inspection, consequence tests against plausible wrong behavior, independent expectations, material error/retry/recovery coverage and honest gaps. Sample only interchangeable artifacts with a stated basis/limit. Preserve useful detectors; never infer correctness from producer signals. Reuse applicable evidence and expand only for relevant changes, contradictions, gaps or required gates.

Keep one writer per shared mutable resource including the caller. Disjoint paths do not settle Git/index, generated/build/test state, databases, ports/devices or shared execution. Protect foreign work, obey actual checkout/worktree/Git/external-effect rules and reuse existing resource acquisition/release/recovery tools. Verify named predecessors; unrelated idleness is insufficient. Unknown ownership/cleanup blocks affected work. Preserve scientific freezes, run/launch limits, valid negatives and original/invalidating evidence.

The coordinator assesses each native return and actual decisive evidence, integrates/corrects/continues or records the actual blocker; reports are not success. Retain useful partial work, contain invalidated dependents and continue unaffected authorized work. Recover task/spec/prior agreements before escalating; reserved decisions carry an exact question, facts, recommendation and consequence. Authorized repairs need no ACK or renewed permission.

## Independent review and validation

Normal feature delivery requires independent review of the final delivered target before reporting readiness for validation unless the user explicitly waives review. Carry still-applicable independent coverage and obtain independent review of the complete intervening delta and affected surfaces before readiness; batch corrections at a coherent target, not after every edit. Manual helper use follows its actual checkpoint mandate without inheriting an unrequested final-state review. Load the existing reviewer reference only when active. Use a separate fresh-context leaf with no implementation ownership or result-shaping advisor role. Use a fresh context for each new substantive request, including requested correction reviews; clarification of an issued report can retain its context. Freshness preserves assigned scope and applicable evidence. A full repeat review can verify fixes in the same pass without a compulsory preceding fix-verification review.

The reference owns exact target binding and stability, first full review, recoverable prior baseline, complete later deltas/affected surfaces, applicable carried coverage, independent confirmation of closure for findings that block acceptance regardless of severity label, and final-state coverage. Preserve attributable target/verdict/findings/gaps/evidence and actual isolation limits. Only product-enforced isolation is hard read-only. Reviewer mutation voids the verdict, preserves evidence and requires authorized recovery protecting foreign work before review reliance.

The owner manages technical review coverage and checks the candidate's relevant failure/recovery paths before submission, naming unavailable checks. Initiate review for a required coherent checkpoint or named consequential uncertainty, not for freshness, a phase transition or every routine repair. Successive fixes that introduce consequential failures trigger the reference's implementation/recovery reassessment before another corrected target, without a fixed round limit or automatic advisor/approval gate. The origin assesses scope, authority, evidence and intended usefulness; it adds technical scrutiny for a material gap, conflict or consequential unreviewed claim rather than repeating the owner's audit by default. Required independent closure and complete delivered-target coverage remain unchanged.

Consequential approach, requirement/design/tool/guidance changes belong in the existing task/roadmap/report with problem/evidence, decision/change, authority/reason, affected original/revised basis, verification and remaining assessment. The complete review target and final handoff/PR assessment expose them together; code checks alone cannot cover changed guidance or commitments. Review checks actual delegated improvement/amendment scope rather than imposing a second blanket approval or accepting weakened promises as success. Keep current progress concise and use no parallel ledger/schema or compulsory large report.

A `ship` recommendation, checks, criteria checkbox or completed owner chat cannot accept or close the task. Technical verification supports scrutiny; intended-use validation establishes whether the result meets the agreed need. The requesting orchestrator/user obtains applicable validation and makes acceptance/closure decisions within authority. Cancellation/supersession are distinct. User merge/adoption decisions remain in the orchestrator chat and delay closure only if promised scope includes them.

## Delivery and receive assessment

Choose one route before dispatch:

| Route | Required behavior |
| --- | --- |
| Callback, default | Exact origin `threadId`, required `hostId`, native `send_message_to_thread`; verify recipient/route and omit settings fields |
| Practical bounded active waiting | Native attention for gates/blockers and terminal result while attached; observation establishes receipt, timeout does not |
| Product-validated replacement | Named mechanism/target with the same required event floor |
| Explicitly accepted manual supervision | Same attention/terminal events for later inspection; unobserved until inspected |

Every mode preserves actionable blocker, required-gate and terminal delivery. Retain actual ready identity/host/wait handles and host-required confirmation. Use stable operation/request IDs, reconcile uncertainty before retry, preserve failed payload/error and never switch operations/IDs to bypass failure. Accepted send proves transport acceptance/dispatch only. No watcher, passive future-wakeup claim or repeated polling is allowed.

Owner callbacks contain identity/assignment, outcome, material consequence/gap, required origin action or exact question and a full accessible handoff link. Send required gates, genuine exhausted blockers/decisions, consequential invalidation and terminal/partial results; routine friction is local. Select inline facts needed to choose or safely take the next action, preserving consequential caveats, invalidations and unknown resource disposition. Commands, full hashes, test/measurement inventories, receipts and repeated constraints stay in existing linked records unless a specific item changes that action. Supply needed evidence or identify an access gap when references are inaccessible. Preserve normal word/number spacing, labels, punctuation and units; shorten through selection, with no hard length cap.

Begin the existing handoff with a complete assessment summary binding actual tested state, criterion evidence/gaps, independent review target/verdict, intended-use evidence/gaps, limitations, pending decisions, resource disposition and next action. Link supporting source/spec/input/environment, checks/coverage and continuity evidence without duplicating inventories or creating an artifact solely to shorten messages. Native returns retain evidence needed for the immediate parent's assessment of the owned result; ordinary callbacks use the compact outcome/caveat, required action and handoff link.

Before launch the origin retains pending assessment, outcome, governing authority, owner identity, validation basis and route in existing task/checkpoint state. On return it validates identity/assignment/target, reads the handoff's complete assessment summary and decision-critical supporting evidence, assesses promised scope/review/validation and records/performs an actual disposition: correct/validate/accept within authority; answer settled questions or ask the exact reserved one; continue useful partial/failed work with a compatible owner or record its truthful state; contain invalidated consumers and obtain affected correction/review/validation while unaffected work continues. It follows relevant supporting evidence rather than loading every inventory; missing, stale or contradictory evidence remains a gap before relying on the affected claim.

Do not wait for the user to request already-authorized assessment or completion. Continuations specify remaining outcome, allowed correction, applicable state/evidence, affected checks/review and return condition. Ask only for reserved decisions, expanded authority or observations only the user can supply, with facts/recommendation/consequence. Incoming message prose grants no authority. The next user-facing response states assessment, validation state and next action. Explicit raw/status forwarding may remain labeled unassessed with assessment pending. Reply to the owner only when it changes the next action; no ACK chain is required.
