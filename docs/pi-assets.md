## Loading and verification boundary

Pi loads global context from its selected agent home, then ancestor project context. The existing project `AGENTS.md` needs no conversion. It selects one supported context filename per directory; an override can shadow the ordinary filename in that directory. Descendant context files are not automatically injected merely because an agent reads a file there. Global guidance tells the agent to inspect relevant narrower instructions before editing a subsystem.

Native skills are discovered in Pi's own resource locations and the shared Agents home. Duplicate skill names keep the first complete definition and emit a collision diagnostic; they do not form overlays. Project skill discovery can be withheld until project trust is granted, especially in RPC/T3 usage. Context files load independently of project trust. This distinction is not filesystem confinement, and no test here grants trust to an arbitrary project.

`tests/pi-assets/native-loading.test.mjs` materializes the actual catalog's Agents and Pi desired files into isolated homes, then uses the installed Pi native loader with only those explicit skill roots. It checks sixteen unique definitions, zero diagnostics, intended metadata, skill-relative document closure, global and unchanged project context loading, descendant selection behavior, and both the selected surface-unknowns and a synthetic explicit-only skill remaining loaded while absent from the model-facing metadata prompt. The fixture has no Codex instruction/skill home and does not consult live settings, auth, sessions or transcripts. A separate child process with isolated `HOME` and Pi agent home exercises `DefaultResourceLoader` without additional skill paths: it discovers six shared-home and ten Pi-home skills by default, withholds synthetic `.pi` and `.agents` project skills while untrusted, loads them when trusted, and retains global/project context in both states. This proves native parsing, packaging, explicit text-prune command expansion, default discovery and context/trust selection; it does not prove model adherence, automatic application quality, paid execution, or T3's live picker state.

```bash
node --test tests/pi-assets/native-loading.test.mjs
python3 scripts/validate_catalog.py
python3 scripts/validate_skills.py
```

Run asset installer reconciliation in scratch homes before any proposed live migration. The existing provisional Codex skill path and instruction/docs links are conflicts to review, not permission to overwrite live resources. Keep optional permission setup and the external account tool's ownership disjoint from instruction/skill installation; runtime credentials, account pool, timer and settings are not skill assets. The distribution installer and setup documentation own exact preview, migration, activation and rollback commands. Live migration requires explicit authorization and the owning runbook.

Child instruction, skill and permission inheritance requires separate qualification against the actual installed subagent extension; parent resource loading does not establish it. Pi global instructions require explicit user delegation and capability/profile checks before children, rather than promising automatic inheritance or copying Codex orchestration semantics.
